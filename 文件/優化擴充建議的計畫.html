A-01　Storage 並行下載 / 上傳 P1

問題

Supabase Storage 備份目前是單線程逐檔下載 / 上傳。幾千個檔案要等很久。

建議

  • 用 p-limit 控制並行度（例如 8 同時）
  • 大檔走 streaming，小檔走 in-memory
  • 進度顯示要對應改成 atomic counter

影響檔案

Node：lib/supabaseStorage.js　|　.NET：Services/SupabaseStorageService.cs

A-02　Dump 寫盤 buffer 加大 + 可選壓縮 P2

  • FileStream buffer 從 64KB 加到 1MB（或 4MB）
  • 加 option --gzip → 直接寫成 db.sql.gz，少 70% 容量
  • 多 DB 匯出已是 zip，內部單檔再 gzip 是 overkill

A-03　SSE / WebSocket 進度推送 P2

問題

前端每 800ms poll 一次 /api/jobs/:id。長 job 會送幾百次 request。

建議

  • 改 SSE：GET /api/jobs/:id/stream → 每行 progress 立刻推
  • WebSocket overkill — SSE 對單向推送夠了
  • fallback：browser 不支援 / 連線斷 → 退回 polling

影響範圍

後端：route + JobService 加 emit。前端：pollJob() 改成 EventSource。

A-04　License heartbeat 改 long-poll / SSE P3

客戶 1000 人 → 每 30 秒 heartbeat → 33 req/秒。SSE long-connection 一個就夠。

規模沒到不必做。

B-01　加入單元 / 整合測試 P0

現狀

0 個測試。每次改完都靠手動點擊。

建議

  • Node：vitest（速度快、API 像 jest）
  • .NET：xUnit + WebApplicationFactory（in-process testserver）
  • License Server 同上
  • 第一批要寫的：
    • License gate middleware：每個 mode + feature 組合
    • Adapter contract test：每個 adapter 都跑同一份 dump→restore→verify
    • Auth 流程：register → verify → login → heartbeat → kicked
  • 整合測試 docker-compose 起 5 種 DB 跑 adapter

B-02　CI 加 lint + 自動測試 P1

現有 .github/workflows/ci.yml 只跑 build。加：

  • Node：eslint . --max-warnings 0 + vitest run
  • .NET：dotnet format --verify-no-changes + dotnet test
  • 結合 GitHub branch protection：必過才能 merge

B-03　structured logging P1

目前 console.log 散在各處，prod 看 log 像散文。

  • Node：pino（快、JSON 輸出）
  • .NET：Serilog + JSON 格式
  • 欄位：requestId / userId / event / latency / ip
  • VPS 直接 ship 到 Loki / Datadog / Better Stack

B-04　Audit log 拆表 P2

event_log 現在混了 debug 跟 audit。拆成：

  • audit_log：合規重要（login / plan_change / kicked）
  • activity_log：debug 用（heartbeat、查詢）

B-05　Plugin 沙箱 P3

目前 plugin 跑在主 process 內，能做主程式能做的所有事。第三方 plugin 可能搞砸。

  • Node：vm2（已 deprecated，要找替代）/ isolated-vm
  • .NET：AssemblyLoadContext 隔離 + SecurityPermission
  • Marketplace 出現後再考慮，自寫 plugin 先不用

C-01　部分 table 多選匯入（真實做篩選） P0

問題

目前 import inspect UI 上有 table checkbox 可勾，但「執行匯入」會跑整份 SQL 檔。勾選沒作用。

建議

  • 後端：/api/import/run 接受 tables: [...]
  • 實作：parse SQL 檔，只執行 CREATE TABLE / INSERT INTO 在指定 table 名單裡的 statement
  • 注意 FK 順序、相依性

難度

SQL parsing 不簡單。可以先用簡單的 USE / DROP / CREATE / INSERT 模式比對。完整 parser 用 node-sql-parser 或 Microsoft.SqlServer.TransactSql.ScriptDom。

C-03　Schema diff 工具 P2

給定兩個 DB connection → 比較 schema → 輸出 ALTER TABLE script。

  • 適合「dev → staging → prod 推 schema 變更」工作流
  • 新增 POST /api/diff endpoint + 新前端 tab

C-04　綠界 / TapPay 支付 P1

Stripe 有信用卡，但台灣 ATM 轉帳 / 超商繳費需要綠界。

  • license-server/routes/billing-ecpay.js — POST 表單 + CheckMacValue + return URL handler
  • 對應 plan upgrade 邏輯跟 Stripe 一樣

C-05　2FA / passkey 登入 P2

  • 2FA：用 TOTP（Google Authenticator）— otplib npm
  • passkey：WebAuthn 標準 — @simplewebauthn/server
  • 都加在 license server 的登入流程

C-06　使用者面板（不只 admin） P2

目前只有 admin web UI。客戶看自己的：

  • 目前 plan、剩餘天數
  • 已登入的裝置（IP）
  • 強制登出其他裝置
  • 升級 plan（按 Stripe checkout）
  • 變更密碼

C-07　Plugin marketplace P3

UI 上「新增 plugin」→ 貼 GitHub URL → 後台 git clone 到 plugins/

  • 需要：plugin.json metadata、簽章驗證、permission scopes
  • 可開「精選 plugin 列表」白名單做為起步

C-08　支援 NoSQL P3

  • MongoDB：mongodump 等價的 JSON dump + restore
  • Redis：BGSAVE 或 SCAN + dump key/value
  • Adapter 介面要加變化（NoSQL 沒有 schema 概念）

市場小但對特定客戶有價值。

C-09　排程備份 P2

實際情境

客戶常見需求：每晚 2 點自動 dump 整個 DB → 上傳 S3 / 寄 email 連結。

實作

  • 新 tab「排程任務」
  • 後端 cron 排程器（node-cron）
  • 支援目的地：本機檔、S3、Supabase Storage、寄 email link
  • 排程紀錄存 SQLite

這是高價值功能，企業客戶會願意為這個升級 plan。

C-10　桌面版 P3

  • Electron 包瀏覽器 + Node — 一個 .exe，零配置
  • Tauri 用 Rust + WebView — 體積小但需要 Rust 環境
  • 適合「不想搞 server」的個人客戶

🎯 推薦執行順序

  1. 立刻做（P0）：B-01（測試）+ C-01（部分 table 多選匯入）— 一個是品質基礎，一個是用戶常抱怨的痛點
  2. 下一個 sprint（P1）：A-01、B-02、B-03、C-02、C-04 — 性能 / CI / log / DDL 完整化 / 台灣支付
  3. 1.0 之前（P2）：A-02、A-03、B-04、C-03、C-05、C-06、C-09 — 重要但非阻擋發布
  4. 之後再說（P3）：剩餘的 C 系列大功能
